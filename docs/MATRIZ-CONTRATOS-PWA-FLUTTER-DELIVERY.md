# Matriz de contratos PWA, CRM Flutter y Delivery

## Ampliación: tiendas, reglas y comunicación

Contrato completo en [RED-TIENDAS-RECOGIDA-CONTRATOS.md](RED-TIENDAS-RECOGIDA-CONTRATOS.md). `suppliers` y `product_suppliers` ya permiten una relación muchos a muchos, pero sus rutas no imponen `company_id`. `supplierKey` incluye teléfono y `DELETE` elimina físicamente; ambos requieren migración. El filtro Tienda y el vínculo por línea faltan en el POS único. `order_pickups` es abastecimiento y no parada courier. `createRoadRouter` calcula distancia vial si está configurado; no existe una regla general aprobada que convierta esos metros en tarifa cliente y pago courier.

**Fuga P0 comprobada en la revisión de origen:** `server/suppliers-routes.mjs` deja entrar a quien tenga `delivery.tracking.start` y las respuestas de `GET /api/admin/suppliers` y `GET /api/admin/suppliers/:id` contienen `phone`. Esta rama aislada ya rechaza esas rutas para courier; la corrección requiere integración y prueba de API en el backend destino. El DTO de parada debe seguir una lista blanca. `courierOrderDTO` no copia el teléfono de `pickup`, pero eso por sí solo no protege otras rutas. El canal «Contactar tienda» todavía no existe.

## Reglas de compatibilidad y evidencia

- El proceso activo `127.0.0.1:8815` solo se identificó como Node PID 27836 con comando relativo `server/crm-server.mjs`; **no se acreditó su revisión ni sus endpoints en vivo**. Las pruebas de esta rama usan `startCrmServer({port:0,dataFile:temporal})` con DB ficticia; no atribuyen cambios al 8815.
- `crm-pos-fullpos/server/crm-server.mjs` y `PHYTOEMAGRY-candidato/server/crm-server.mjs` son dos versiones de un archivo de alta colisión, ambas modificadas localmente. El ancestro común es `bb53861`; la integración debe hacerse por contrato y fragmentos revisados por el dueño del backend.
- La clave fija de Delivery no puede cubrir una segunda intención legítima tras reasignación. Reintento conserva la clave de esa intención; nueva intención genera otra clave y exige huella/versión.
- La UI no debe inferir `paid` a partir de `delivered`, ni remuneración a partir de `delivery_fee`, ni una rendición a partir de cerrar turno.
- No se ejecutaron HTTP, SQL ni pruebas funcionales para esta matriz. Los casos medibles están en [UAT-INTEGRACION-ECONOMICA.md](UAT-INTEGRACION-ECONOMICA.md).
